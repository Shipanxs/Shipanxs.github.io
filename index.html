三、实验原理

1. 分词：jieba 精确模式 + 自定义词典

jieba 先按前缀词典构造有向无环图，再用动态规划找最大概率路径；词典里没有的词，用 HMM 按字的位置概率兜底。所以”精确模式”并不等于”一定准”：领域词只要没进词典，就会被切碎。

比如”不可哈希”在默认词典里不存在，会被切成”不可 / 哈希”；”列表推导式”也会散成”列表 / 推导 / 式”。这类词一旦被切碎，词频统计就会失真。解决办法有两个：jieba.add_word() 临时加词，或者 jieba.load_userdict() 加载整份词典。

2. 词频与词云

词云本质上是对词频做视觉编码：词越大，出现次数越多。generate_from_frequencies() 接收一个 {词: 频次} 字典，max_words 控制展示数量，font_path 必须指向中文字体，否则全是方框。

collocations=False 要关掉，不然 wordcloud 会自动把相邻词拼成”人工智能”这种双词短语，中文语料里很容易出现莫名其妙的组合。中文还有一个坑：默认允许 10% 的词竖排，汉字一旋转就读不出来，所以我把 prefer_horizontal 设成 1.0，全部横排。

3. 抽取式摘要

没有接大模型，摘要用的是最朴素的抽取式做法：

  1. 按句号、问号、分号、换行切句；
  2. 每句话里的词，按全局词频加权求和；
  3. 除以句子长度的 0.6 次方做惩罚，避免一句话越长分越高；
  4. 取分数最高的 3 句，按原文顺序拼起来，超过 100 字截断。

它不会改写，只会”挑句子”，所以读起来偶尔跳跃，但不会编造原文里没有的东西。

4. 规则化审查

审查意见由四条规则拼出来：

  • 正文少于 300 字 → 篇幅偏短；
  • 最高频词占比超过 8% → 高频词重复度偏高；
  • 平均句长超过 60 字 → 长句偏多；
  • 命中 TODO、待补充、XXX、占位 → 存在待完善占位。

规则很笨，但胜在可解释：每条意见都能指出是哪条规则触发的，不会给一个”感觉写得不太好”这种没法改的结论。

5. Agent 化：和普通脚本差在哪

普通脚本的假设是”输入是对的”；Agent 原型要自己处理输入的不确定性：

  • 编码不确定 → UTF-8、UTF-8-SIG、GB18030 依次尝试；
  • 字体路径不确定 → 按 msyh.ttc、simhei.ttf、Arial Unicode 的顺序找；
  • 文件坏了 → 跳过并在终端说明，不中断整批任务；
  • 输出要能被别的程序接 → 固定 CSV 字段，UTF-8-SIG 保存，Excel 直接打开不乱码。

九、思考题

1. 为什么统计词频前要先过滤单字和停用词？如果不过滤会怎样？

中文里”的、了、是、在”这类词出现频率极高，但几乎不携带主题信息。不过滤的话，Top 50 会被虚词和单字占满，词云看起来热热闹闹，实际上什么也没说明。单字还有一层问题：中文单字歧义大，”行”可能是”银行”也可能是”可行”，单独统计没有意义。所以过滤规则是：长度小于 2 的词不要，停用词表里的不要，纯数字不要。

2. 自定义词典和停用词表冲突时，以谁为准？

当前实现是先分词、再查停用词，所以停用词优先：一个词就算被词典收录，只要在停用词表里，还是会被丢掉。如果某个术语必须保留，正确做法是把它从停用词表里删掉，而不是指望词典覆盖。分词质量可以用小样本人工标注来评估：抽 20 句，人工标出正确切分，算准确率和召回率；更省事的办法是看 Top 关键词是否符合你对这批文档的预期。

3. 抽取式摘要的天花板在哪？什么情况下必须接大模型？

抽取式只能”选原句”，不能合并、改写、消解指代，所以句子之间经常跳跃，遇到跨段落推理就无能为力。它适合”快速知道这篇讲了什么”，不适合”给我一份能直接发出去的综述”。如果要生成式摘要、要回答”这篇文档里的方案有什么风险”这种问题，就得接大模型；但要把原文和关键词一起放进 Prompt，并要求它只基于给定材料回答，否则很容易编。

4. 如果文档从 4 篇涨到 1000 篇，当前实现最先撑不住的是哪一步？

先是内存：all_tokens 把全部词都存下来，1000 篇就是线性增长；其次是串行 IO 和每篇一次 jieba.lcut，速度会明显变慢；词云反倒不是瓶颈。改造方向是流式统计（读完一篇就更新 Counter，不保留全量 token）、分批处理、多进程分词，以及给已经分析过的文件做缓存。

十、实验小结

这次最值钱的不是”会写词云”了，而是把一堆看似零散的小判断写进了流程：编码要回退、字体要兜底、表格要清洗、停用词要按语料改、摘要要防长句、审查要能解释。所谓 Agent，很大一部分就是这些”如果……就……”的工程细节，而不是模型本身。

现在的版本还是个规则原型：摘要靠抽句，审查靠阈值，没有接大模型，也没有文件监控。下一步想试两件事：用 watchdog 监听文件夹，新文章一落盘就自动生成审查报告；再把关键词和摘要喂给大模型，让它输出真正的修改建议，而不是”篇幅偏短”这种我自己也能看出来的结论。

Python实验-列表、元组与集合

2026-11-22

这次实验的主题是三种最常用的容器：列表、元组、集合。题目看起来都是”基础语法”，但真跑起来，切片删除的索引规则、嵌套容器的哈希判定、边遍历边删除的漏删问题，一个比一个反直觉。下面是完整的实验过程、真实运行结果和原因分析。

一、实验目的与环境

目的：掌握 list / tuple / set 的可变性与可哈希规则；弄清切片删除、步长正负的执行逻辑；熟练使用集合运算与推导式；能独立排查 TypeError: unhashable type 这类问题。

环境：Python 3.12（CPython），Windows 11，无第三方库依赖。

二、实验原理（先记住这四条）

  1. list 是动态数组，存的是对象引用；切片生成新列表，del ls[切片] 是原地批量删除。
  2. tuple 的”不可变”指元组保存的引用地址不能改，不限制引用指向的对象内部被修改。
  3. set 用哈希表实现，元素必须可哈希；set 本身可变，所以不能嵌套；frozenset 不可变、可哈希，可以放进集合。
  4. 可哈希的本质是：对象在生命周期内哈希值不变。

九、必答思考题

1. del ls[::3] 是按删除前索引还是动态实时索引？

按删除前的索引一次性计算。切片会先确定下标集合 {0,3,6,9}，再统一删除这些位置。如果理解成动态索引，删掉 0 之后原下标 3 已经不是同一个元素，结果会和实际不符。

2. t=(1,[2,3])，为什么 t[1].append(4) 合法，但 t 不能放进集合？

元组的不可变指的是”元组保存的引用不能换”，不是”引用指向的对象不能变”。t[1] 仍指向同一个 list，往这个 list 里 append 不改变元组结构，所以合法。但哈希要求整个对象可哈希，list 不可哈希，因此元组整体也不可哈希，不能放进 set。

3. 为什么普通 set 不能嵌套，frozenset 可以？

set 是可变对象，内容一变哈希值就变，这会破坏哈希表”桶位置稳定”的前提。frozenset 一旦创建就不能修改，哈希值固定，因此可以安全地作为另一个集合的元素。

4. for 遍历同时 remove 为什么会删不干净？安全方案？

迭代器内部维护一个自增下标，remove() 让后面的元素左移，于是每删一个就有一个元素被跳过。安全方案：用列表推导式重建、遍历副本 ls[:]、或用 while 手动控制索引。

5. list(set(数据)) 去重的缺陷？保序去重有哪些实现方式？

缺陷有两个：顺序丢失；元素必须可哈希（嵌套列表这类直接报错）。保序方案：手写 not in 循环、dict.fromkeys(data)、OrderedDict（3.7 之后普通 dict 已保序）。

十、实验小结

容器 有序性 可变性 元素重复 可哈希
list 有序 可变 允许 不可哈希
tuple 有序 不可变 允许 取决于元素
set 无序 可变 不允许 自身不可哈希
frozenset 无序 不可变 不允许 可哈希

二、一笔画的数学条件

为什么偏偏是”隔 3 个”？这其实是一个模运算问题：

  • 每次前进 STEP 个顶点，位置按 (k × STEP) mod N 变化；
  • 当 gcd(N, STEP) = 1（互质）时，STEP 的倍数能遍历 0 ~ N-1 所有余数，一次走遍所有顶点并闭合 → 一笔画；
  • 当 gcd(N, STEP) > 1 时，只能走到一部分顶点就闭合，剩下的要另起一笔。

对照几个例子：

五角星 {5/2} 1 一笔闭合
六角星 {6/2} 2 两个三角形，两笔
八角星 {8/3} 1 一笔闭合
九角星 {9/4} 1 一笔闭合
十角星 {10/4} 2 两个五角星，两笔

所以”一笔画”不是靠手稳，而是由顶点编号的步长和顶点数决定的。

python实验-蒙特卡罗方法手搓图形

2026-11-22

这次的实验题目是”用蒙特卡罗方法估算 π，并把过程画出来”。一开始以为要写一大堆循环和判断，真动手才发现核心逻辑只有四五行，剩下的时间基本都花在调图上——中文乱码、圆被压成椭圆、图例把散点挡住，一个比一个磨人。

一、思路：把 π 藏进一个面积比里

在 0 到 1 的正方形里随便撒点，再画一个以原点为圆心、半径为 1 的四分之一圆，那么：

  • 正方形的面积是 1；
  • 四分之一圆的面积是 π / 4；
  • 点撒得够多、够均匀时，”落在圆内的点数 / 总点数”就近似等于”圆面积 / 正方形面积”，也就是 π / 4。

反过来推一下，π ≈ 4 × 内点数 / 总点数。整个算法就这一句话。

二、代码实现

几个值得记下来的写法：

  1. 不要用 for 循环。 np.random.rand(n) 一次性生成 n 个 [0,1) 的随机数，numpy 的向量化运算比 Python 循环快一两个数量级，撒 100 万个点也就零点几秒。
  2. inside = x**2 + y**2 <= 1 是布尔数组。 拿它当下标 x[inside] 就能直接取出所有圆内的点，不需要另建列表。
  3. 判据用 <= 1。 落在圆周上算”内”还是”外”其实无所谓，边界上的点概率为 0，对结果没有影响。
  4. 统计用 inside.sum()。 布尔数组求和会把 True 当 1、False 当 0，直接就是内点个数。

三、跑出来的结果

这次取 n = 10000，落在圆内的点有 7837 个，估算值：

π ≈ 4 × 7837 / 10000 = 3.1348

和真值 3.14159 差了 0.0068。图上蓝色点密密麻麻挤满左下角的扇形，红色点全部堆在右上角那一块——视觉上一眼就能看出”面积比 ≈ 概率比”这件事。

四、画图踩过的坑

代码逻辑五分钟就写完了，图却改了半小时，问题都出在细节上：

  • 中文变方块、负号消失。 必须提前设 font.sans-serif = ['Microsoft YaHei']（Windows 上 SimHei 也行），再设 axes.unicode_minus = False，否则标题里的中文和负号都会出问题。
  • 圆被压成椭圆。 matplotlib 默认按画布比例拉伸坐标轴，一定要加 set_aspect('equal')，否则半径 1 的圆看着像个扁馒头。
  • 图例压住散点。 一开始图例放在图里，正好盖住右上角的红点。改成 bbox_to_anchor=(1.05, 1), loc='upper left'，图例就挪到了图外右侧；figsize 从 (5, 5) 调成 (6, 5)，给它留出位置。
  • 图例的点太小。 散点本身 s=1，图例里的示例点也跟着变成一个小像素，根本看不清。markerscale=8 把它单独放大八倍。
  • 图例被裁掉一半。 图例移到图外后，保存时右半边会丢，加一句 plt.tight_layout() 让布局自动收缩。
  • 点糊成一片。 点一多，s=1 也会互相重叠，这是密度高的必然结果，反而正好体现了”越密越接近理论面积”。

五、误差分析

蒙特卡罗的误差是统计性的，不是代码写错了。n 个点时的估计标准差大致是

σ ≈ 4 × √(p(1-p)/n)，其中 p = π/4 ≈ 0.785

代入 n = 10000，σ ≈ 0.016，相对误差约 0.5%。这次的偏差 0.0068 还不到半个 σ，属于非常正常的一次抽样。这也解释了为什么它收敛得”慢”：误差按 1/√n 下降，想让误差减半就得撒四倍的点，想多要一位小数的精度，n 得涨一百倍。

六、小结

蒙特卡罗方法最迷人的地方在于它”绕过”了推导：不用积分公式，不用级数展开，只要会生成随机数、会数点，就能算出 π。代价是精度提升极慢，1/√n 这条曲线注定了它不适合要求高精度的场合，但在高维积分、复杂边界这类传统方法算不动的问题上，它反而是最省事的选择。

看板版面划分为四大模块：数据概览区（KPI 数据卡片）、维度统计区（分类对比与占比图表）、趋势分析区（时间序列图表）、明细数据区（订单与商品明细表）。

整体采用深色科技风配色：背景色 #0d1117、卡片底色 #161b22、主色 #00d4ff（数据强调）、辅助色 #ff6b35 与 #a855f7（预警与对比）、文本色 #e6edf3 与 #8b949e，保证视觉层级清晰、信息降噪。

第7章 面向对象设计原则——单一职责原则与开闭原则

耿祥义、张跃平《Java面向对象程序设计（第4版）》第7章

一、什么是面向对象设计原则？

在面向对象程序设计中，除了掌握继承、多态、接口等语法特性外，更重要的是理解面向对象设计的原则。这些原则是前人总结出的经验法则，指导我们如何设计出可维护、可扩展、可复用的软件系统。

本章介绍两个最基本、最重要的原则：单一职责原则和开闭原则。

二、单一职责原则

2.1 定义

单一职责原则（Single Responsibility Principle，SRP） 是最简单的面向对象设计原则，也是最难正确运用的原则之一。

它的核心思想是：一个类只负责一个功能领域中的相应职责。

通俗地说：一个类，只有一个引起它变化的原因。

2.2 如何理解”职责”？

一个类的”职责”可以理解为”它为什么存在”或”它做什么事情”。

  • 如果一个类有多个引起它变化的原因，就说明它承担了多个职责
  • 职责过多，就会导致类变得臃肿、复杂、难以维护

2.3 违反单一职责原则的后果

当一个类承担了多项职责时，会出现以下问题：

  • 可维护性差：修改某一职责的代码可能会影响其他职责的正常功能
  • 可复用性差：无法单独使用某个职责的功能，因为所有功能都耦合在一个类中
  • 可测试性差：测试一个职责时，必须依赖其他职责的代码
  • 代码臃肿：一个类包含了大量无关的方法，代码量过大

2.4 如何识别违反单一职责原则的类？

可以通过以下几个问题来判断：

  1. 这个类的方法是否涉及多个不同的功能领域？
  2. 修改这个类的某个方法，是否会影响其他不相关的方法？
  3. 这个类的名称是否过于宽泛（如”Manager”、”Util”、”Handler”）？
  4. 这个类是否有多个不同的”使用者”，每个使用者只用到其中一部分功能？

如果上述问题多数为”是”，说明该类违反了单一职责原则。

2.5 课堂作业


三、开闭原则

3.1 定义

开闭原则（Open-Closed Principle，OCP） 是面向对象设计中最重要的原则，由Bertrand Meyer于1988年提出。

它的核心思想是：对扩展开放，对修改关闭。

  • 对扩展开放：当系统需要增加新功能时，可以通过添加新代码来扩展系统的行为
  • 对修改关闭：在添加新功能时，不应修改已有的源代码

通俗地说：写好的代码，不要再动了；要加新功能，就写新类。

3.2 为什么开闭原则如此重要？

在软件工程中，修改已有代码是有风险的：

风险 说明
引入新Bug 修改一处代码可能破坏原本正常的功能
影响其他模块 被修改的类可能被多个其他类依赖，修改后影响范围难以预估
增加测试成本 每次修改都需要重新测试所有相关功能
难以维护 频繁修改的代码会变得混乱，难以理解

开闭原则通过”不修改已有代码，只添加新代码”的方式，有效规避了上述风险。

3.3 如何实现开闭原则？

实现开闭原则的关键是抽象化：

  1. 定义抽象层：使用抽象类或接口定义系统的核心规范
  2. 实现具体类：让不同的具体类实现这个抽象层
  3. 面向抽象编程：客户端代码针对抽象层编程，不依赖具体实现类
  4. 扩展新功能：当需要新增功能时，只需添加一个新的具体类，无需修改已有代码

这一过程依赖Java的多态机制——父类引用可以指向任意子类对象，从而实现”新增子类即可扩展功能”。

3.4 违反开闭原则的后果

当系统不遵循开闭原则时，会出现以下问题：

  • 分支泛滥：大量使用if-else或switch来判断类型，每增加一种类型都要修改判断逻辑
  • 代码重复：相似的功能无法复用，只能复制粘贴后再修改
  • 扩展困难：每次新增功能都要修改多处已有代码，且改动的类和数量不断增加
  • 回归风险：每次改动都可能引入新的Bug，需要重新测试整个系统

四、两个原则的对比总结

对比项 单一职责原则 开闭原则
核心思想 一个类只做一件事 对扩展开放，对修改关闭
关注点 类的内部职责分配 系统的可扩展性
解决问题 类的臃肿和高耦合 新增功能时被迫修改已有代码
实现方式 将多个职责拆分到不同类中 引入抽象层，利用多态扩展
目标 提高可维护性、可复用性 提高可扩展性、降低修改风险

单一职责原则解决的是类的设计质量问题，开闭原则解决的是系统的可扩展性问题。两者相辅相成——遵循单一职责原则设计的类，通常也更容易符合开闭原则。
